## 2. 真实 GDD 的目录示例

0 A.D. 是开源 RTS，非组装对战。本轮线上页面受 Anubis 拦截，实际依据是旧快照：

- 原站：https://trac.wildfiregames.com/wiki/Design_Document
- 本次读取：http://web.archive.org/web/20241223133357/https://trac.wildfiregames.com/wiki/Design_Document

主要目录为：

```text
Licensing and Disclaimer
Background
  The Vision / War Story / Territories
Playable Civilizations
Other Civilizations
Lists
  Entities: Nature / Entities: Player / Maps
Entities: Traits
  ID / AI / Armour / Health / Population / Supply / Vision 等
Entities: Actions
  Attack / Create / Gather / Heal / Move / Patrol 等
```

它明确说明这是计划，平衡调整或范围削减可能导致成品不同。对本项目可讨论的借鉴是：把“玩家追求什么”“有哪些内容”“对象有什么属性”“对象能做什么”分别写清；维护计划与实现的差异。不是要求先设计文明、地图或完整世界观。

## 3. 从方法到本项目问题

### MDA：先问体验，再检查规则

原文：https://users.cs.northwestern.edu/~hunicke/MDA.pdf

Mechanics 是规则与数据，Dynamics 是规则交互后的运行行为，Aesthetics 是玩家期望获得的体验。它允许多种体验并存，没有统一的比例配方。

在本项目中，“发现奇怪组合”“表达自己的小鸡”“解决敌人威胁”“探索并持续成长”可以是不同目标。这些只是候选，需要用户确定优先级；不能先定一堆战斗轴和容量，再假定它们会自然带来目标体验。

### One Page Designs：用关系图补充文字

- GDC 摘要：https://www.gdcvault.com/play/1012356/One-Page-Designs
- 幻灯片：https://www.stonetronix.com/gameconnection-2015/OnePageDesigns.pptx

材料包含流程图、故事板、时间与空间、关系、矩阵等表达方式，也明确说明一页图不能替代所有书面描述。演讲中的 Design Bible 目录是对照例，不是行业强制规范。

候选用法：一页循环图用于讨论整局；组合矩阵用于看协同与冲突；规则卡和参数表负责实现细节。是否需要为每个系统画图，按讨论需要决定，不额外制造维护负担。

### The Door Problem：把概念拆成实际问题

原文：https://lizengland.com/blog/the-door-problem/

“游戏里有门”还涉及能否锁、谁能开、多个角色同时到达会怎样。对应到“翅膀可以飞”，还要追问起降、命中、重复翅膀、冲突与双方无法攻击等情况。

这是列问题的方法，不是要求加入飞行；列出边界后由用户决定哪些规则进入范围。

## 4. 相近游戏带来的讨论

| 游戏 | 已核验的做法 | 本项目可讨论的问题 |
|---|---|---|
| Super Auto Pets | Arena 异步无计时；Versus 同步 8 人；不同包 | 是否让玩家从容构筑？固定挑战池与自由池是否分开？ |
| Backpack Battles | 购买、合成和摆放共同影响构筑；准备可无计时 | 装配的取舍来自哪里？准备慢是否妨碍整体节奏？ |
| Nimbatus | 战役、沙盒与竞技；独立编辑器不含任务和行星 | 能否先单独验证装配与试跑，再决定长流程？ |
| TerraTech | 探索、资源、任务与可破坏方块；另有创造模式 | 世界如何反哺改装？损失、维修和返程是否值得加入？ |

前两款的自动对战与后两款的实时探索不同，不能把四款归纳为同一种战斗节奏。案例的零件数量也不能直接决定本项目要扩多少内容。

## 5. 本轮提出的适配方式

下列为工作提案，不是玩法定案：

- 先由用户选核心乐趣与首轮循环，再写规则，避免预设关卡制、商店制或大世界。
- 用一条可完整走通的过程研究流畅性：玩家知道什么、能决定什么、看到什么后果、输后怎么改、为何再来一次。
- 规则写到可推演、可实现、可验证；事实、试验结果和推荐方案分别记录。
- 保留正式设计、研究提案、确认记录与代码状态之间的边界；未确认的方案不回写成正式规则。
- 范围与规则逐步确定后，再做 MECE 需求归属、状态分支与交互覆盖；不在方向未定时堆完整目录。

具体操作见 [玩法设计工作规范](02_玩法设计工作规范.md)，需要用户选择的首批问题见 [现状评估与待确认](03_现状评估与待确认.md)。

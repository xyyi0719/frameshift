# 公开策划文档与设计方法取证

版本 V1.1（2026-11-24）

用途：给「拼装小鸡」的设计文档结构找可核验的一手依据。下面每个来源都标了实际请求结果、能读到的原文内容，以及哪些部分不适用于单只生物装配对战。

本次没有找到任何公开的组装/合体对战类完整 GDD。所以本文不给该品类的成品目录，只给可验证的文档结构与方法片段，适配部分属于建议。

## 结论先行

- 可靠来源 4 个：MDA 原文、Stone Librande 的 One Page Designs 幻灯片与 GDC 官方摘要、0 A.D. 的公开设计文档、Pixel Wheels 仓库文档（反向证据：有 docs 目录但没有 GDD）。
- 1 个平台只到营销页：Dundoc 首页可访问，模板内容要登录，不能作为结构证据。
- One Page Designs 里出现的「Design Bible」目录，是作者用来对照的常见写法，不是行业强制标准；0 A.D. 的目录是该项目的自用结构，同样不是标准。
- 搜索引擎本轮基本不可用：Google 返回需要 JS 的中间页（`/httpservice/retry/enablejs`），DuckDuckGo 返回 202 挑战页，Bing 中文区把查询降级成 "stone" 的词条结果。上述来源全部改为直接请求站点、GitHub API 和 Wayback 快照取得。

## 来源 1：MDA 原文

- URL：https://users.cs.northwestern.edu/~hunicke/MDA.pdf（原地址 http://www.cs.northwestern.edu/~hunicke/MDA.pdf 302 跳到 users 子域）
- 页面标题（PDF 首页）：MDA: A Formal Approach to Game Design and Game Research
- 作者：Robin Hunicke、Marc LeBlanc、Robert Zubek
- 访问结果：200，279,913 字节，5 页。正文流为 ASCII85 + Flate 双层压缩，已解压提取并核对文本；仓库只保留取证记录与短引文，不收录全文副本。
- 来源类型：学术论文，作者自述源自 GDC 2001-2004 的 Game Design and Tuning Workshop。

能核验的内容：

- 三层定义，原文（引用）：
  - "Mechanics describes the particular components of the game, at the level of data representation and algorithms."
  - "Dynamics describes the run-time behavior of the mechanics acting on player inputs and each other's outputs over time."
  - "Aesthetics describes the desirable emotional responses evoked in the player, when she interacts with the game system."
- 设计师与玩家看同一系统的方向相反：设计师从 mechanics 推向 dynamics 再推向 aesthetics，玩家先接触 aesthetics。原文（引用）："From the designer's perspective, the mechanics give rise to dynamic system behavior, which in turn leads to particular aesthetic experiences."
- 八类体验目标，原文列表：1 Sensation（Game as sense-pleasure）、2 Fantasy（make-believe）、3 Narrative（drama）、4 Challenge（obstacle course）、5 Fellowship（social framework）、6 Discovery（uncharted territory）、7 Expression（self-discovery）、8 Submission（pastime）。
- 一个游戏同时追求多个目标，原文举了 Charades、Quake、The Sims、Final Fantasy 四例，并说明没有统一配方决定组合与比例。
- 调参段落用 Monopoly 做例子，说明改 mechanics（补贴落后玩家、对领先者加税）来修 dynamics（长期缺乏张力）。

候选适配（待用户确认）：先写目标体验清单（例如 Discovery 对应"试出没见过的组合"，Expression 对应"我的鸡长这样"，Challenge 对应关卡压力），再由体验倒推零件数值、协同规则和战斗时长；评审时按 M/D/A 三层分别写判据，避免只讨论数值表。

不适用：论文不给文档目录，也不谈内容量、排期、商业化。它的八类目标是描述性词汇表，不是评分表。

## 来源 2：Stone Librande 的 One Page Designs

- GDC 官方页：https://www.gdcvault.com/play/1012356/One-Page-Designs
  - 标题：GDC Vault - One-Page Designs
  - 访问结果：200。摘要原文（引用）："a style of design documentation that he calls a one page design. As the name implies, this is a document that is exactly one page long." 并写明讲者会展示来自 "Diablo III, The Simpsons and Spore" 的例子。
- 幻灯片（可下载原件）：https://www.stonetronix.com/gameconnection-2015/OnePageDesigns.pptx
  - 访问结果：200，18,584,017 字节，104 页。已从 pptx 的 XML 文本层提取文字并核对；仓库不收录原件或完整文本副本。
  - 站内另有 GDC 2010 版本：https://www.stonetronix.com/gdc-2010/ 下的 `OnePageDesigns.ppt`（12MB，旧二进制格式，本次未解析）。
- 来源类型：从业者会议演讲与配套幻灯片。作者为 EA/Maxis 设计师，GDC 2010 设计专场。

能核验的内容：

- 第 4 页是 "Design Bible" 的目录样式，标题层级为：1 Game Mechanics（1.1 Core Gameplay、1.2 Game Flow、1.3 Characters/Units、1.4 Gameplay Elements、1.5 Game Physics、1.6 Statistics、1.7 AI、1.8 Multiplayer）、2 User Interface（2.1 Flow chart、2.2 Functional Requirements、2.3 Mock-up、2.4 Buttons/icons/pointers）、3 Art and Video、4 Sound and Music（含 4.1 至 4.3 子项）、5 Story（5.1 Backstory and world、5.2 Character descriptions、5.3 Game text/dialog、5.4 Sample scripts）、6 Level Requirements（6.1 Level Diagrams、6.1.1 Flow diagrams、6.2 Asset revelation schedule）。
- 第 8 页给设计圣经的优缺点：优点之一是（引用）"The act of creating the document is the act of designing the game"；缺点是 "Doesn't scale up"、"Hard to manage updates"、"Difficult to search"。
- 第 14 页给设计 wiki 的优缺点：优点是易更新、可分块、有历史记录；缺点是（引用）"Hides design relationships"、"Low resolution"。
- 第 15 页的理由（引用）："Problem: Most people don't read past the first page or screen. Solution: Only use one page."
- 第 57 至 73 页是表达手法：Flow Charts、Storyboards、Time + Space、Relationships、Matrices。矩阵示例是「Character Class × Faction」，行列为 Archer/Fighter/Mage/Scout/Thief/Warlock 与 Fire/Metal/Nature/Water，格子里打叉表示该职业可用该系技能。
- 第 83 至 97 页列局限（引用）："Hard to keep up"、"Hard to organize"、"One size doesn't fit all"、"Doesn't replace writing"。
- 第 98、101 页列团队与个人收益；第 102 页（引用）："The goal of design is to efficiently communicate ideas."

候选适配（待用户确认）：装配系统可做成关系矩阵页，行是 24 个零件、列是 6 个槽位与标签（wing/light/heavy…），格子里写协同或冲突结果，一眼能看出覆盖缺口；一局流程用流程图；战斗节奏用 Time + Space 式时间轴。参数明细放表格附录，一页图只负责让人看懂关系。

不适用：这套方法解决沟通，不解决数值是否平衡；24 个零件的完整参数压不进一页，硬压会变成看不清的小字。本轮只核验幻灯片文本层，没有验证示例图的完整画面；不能据此断言已读过其中各商业项目的完整内部文档。

能核验的目录（原文层级）：

- Background：The Vision、War Story、Territories
- Playable Civilizations：Athenians、Britons、Carthaginians、Gauls、Iberians、Macedonians、Mauryas (Indians)、Persians、Ptolemies (Egyptians)、Romans (Republican)、Seleucids、Spartans
- Other Civilizations：Celts、Hellenes

可引用的声明（引用）："It represents the current plan for 0 A.D. but the final game might not be exactly as described here due to for example issues found when balancing the game or features cut to make it possible to release the game in a reasonable time." 同页还注明 Traits 与 Actions 的字段细节以实体文档站为准，本页仅作参考。

候选适配（待用户确认）：它把内容拆成「设定 → 阵营 → 实体清单 → 实体属性 → 实体动作」，这个分层可作为参考，改写为「世界观 → 生物 → 零件清单 → 零件属性 → 零件技能」；文档开头放授权与免责声明、说明计划与实现可能不一致，可以作为文档维护提案，不代表必须照搬。Traits 列表里的 Health、Armour、Population、Supply 等字段，与零件表的 hp/def/负重 有对应关系。

不适用：它的规模是 RTS（12 个文明、五类单位、十类地图），组件数量与装配对战差一个量级；Traits 是引擎字段清单，不是玩法说明，照抄会把文档写成配置手册。抓取时线上被反爬挡住，若日后引用需重新核验快照是否仍可访问。

## 来源 4：Pixel Wheels 仓库（反向证据）

- URL：https://github.com/agateau/pixelwheels
- 访问结果：200。用 GitHub API 取 master 分支完整树（926 个条目，未截断）。
- 仓库自述：A top-down retro racing game for PC (Linux, macOS, Windows) and Android.
- `docs/` 下实际文件：android-studio-setup.md、animscript.md、building.md、coding-style.md、credits.md、debug.md、gdxui.md、map-format.md、packaging.md、release-check-list.md、screens.dot、translations.md、vehicles.md。
- 来源类型：开源游戏仓库的工程文档，没有 GDD。

能核验的结论：这个项目有 13 个文档文件，内容分别是构建、编码风格、地图格式、载具参数、翻译与发布检查，属于工程与资源格式说明。`vehicles.md`（1,614 字节）与 `map-format.md`（5,705 字节）是单实体参数和资源格式的写法示例，`screens.dot` 是界面跳转的 Graphviz 图。

候选适配（待用户确认）：可以借 `vehicles.md` 那种「一个实体一节、字段与取值范围并列」的写法来写零件表；`screens.dot` 说明界面流程也能用图描述，与 One Page Designs 的流程图思路一致。

不适用：不能当目录模板或设计方法来源。它恰好说明开源仓库有 docs 目录不等于有策划文档，评估他人项目时不要看到 docs 就当作 GDD。

## 事实与建议分开

事实（可在上述来源原文中核对）：

1. MDA 用 Mechanics/Dynamics/Aesthetics 三层描述游戏，并给出八类体验目标与多目标并存的例子。
2. One Page Designs 主张一页一份设计，理由是多数人只读第一页；给出流程图、故事板、时间空间、关系图、矩阵五种表达手法，并自陈四种局限。
3. 0 A.D. 的公开设计文档按「设定 → 文明 → 实体清单 → Traits → Actions」组织，并声明计划可能与成品不一致。
4. Pixel Wheels 的 docs 是工程文档，没有 GDD。
5. Dundoc 的模板内容不可匿名查看。

建议（我的判断，需要用户确认后才写入正式规范）：

1. 文档分三层：一页系统图用于评审，参数表用于实现，验收清单用于判断改动是否达标。三层各自有版本，避免一页图被当成完整规格。
2. 装配系统的一页图用矩阵表达零件×槽位与标签×协同规则，覆盖缺口靠空格暴露。
3. 战斗系统的一页图用时间轴加事件流，与现有 30Hz 确定性模拟、事件流回放的实现方式对齐。
4. 目录骨架借 0 A.D. 的分层，删掉文明、地图、单位编队这些 RTS 专属层，保留「实体属性 + 实体动作」的写法给零件。
5. 每份文档开头写版本、适用范围、未决问题；参考 0 A.D. 的做法，明确计划与实现可能不同。

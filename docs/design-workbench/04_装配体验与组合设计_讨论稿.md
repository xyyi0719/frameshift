## 2. 复核到的现状

以下来自静态读码，没有新增脚本、运行装配对照或亲自验证操作手感。

| 事实 | 代码入口 | 对讨论的意义 |
|---|---|---|
| 支持点击快装，以及拖到对应部位的槽位环；部件只能进定义的部位 | `src/ui/app.ts`：`PartDrag` 回调、`addPart()` | 已有快捷入口，不应预设必须把每件都精确拖放 |
| 相同零件可重复添加；减号移除该类型最后一个实例；可以清空部位或全部清空 | `src/ui/app.ts`：`removeLast()`、`clearSlot()`、`clearAll()` | 当前以类型和数量编辑为主，不是任意选择某个实体再编辑 |
| 部位内坐标、旋转和缩放由确定性布局计算 | `src/core/layout.ts`：`layoutParts()` 及各部位布局函数 | 当前不是玩家自由定位的机械拼装；要增加微调或结构关系须另定范围 |
| `PartInstance` 只记录定义 ID 与等级 | `src/core/types.ts`：`PartInstance` | 实例位置、连接关系、稳定标识、撤销历史等不能当作已有能力 |
| 每次修改刷新外形、属性与协同提示；提示默认显示前四条 | `src/ui/app.ts`：`refresh()`、`renderNotes()` | 有即时反馈基础，但没有说明每条效果的来源和最终是否真正有效 |
| 当前部件提供数值、标签与部分能力 ID；只有五条内置协同 | `src/data/parts.ts`、`src/core/synergies.ts` | 命名或描述里的动作不能视为已实现的独立战斗机制 |

### 两个会干扰组合理解的例子

`src/core/stats.ts` 的 `resolve()` 先合并全身标签，`matchRule()` 再检查标签是否齐全，标签来源不被保留：

- 羽翼自己就带 `wing` 和 `light`，不需要装精瘦鸡身也能匹配“轻身 + 翼”的规则提示。
- 爪腿自己带 `sharp` 和 `claw`，配短喙也能满足 `beak + sharp + claw`，触发名为“尖喙 + 爪”的规则。

这是静态推导，不是新跑的试验结果。它说明触发条件和文案有歧义，不自动说明用户想要哪一种规则。后续应明确“某部件具备属性”和“全身具备属性”各用在哪里。

另一个现象：当前组合提示可能同时列出滑翔和着地，最终 `canGlide` 会被着地状态覆盖。提示触发、最终生效与实际战斗行为应分开讨论，不能只凭出现提示认定效果发生。

## 3. 装配操作的候选方案

### 3.1 自由度的三个选择

| 方案 | 玩家决定什么 | 收益 | 代价或风险 |
|---|---|---|---|
| 全自动排布 | 选零件、选数量，系统放到对应部位 | 延续现状，进入试验快 | 外形创作主要依靠种类和数量，位置表达受限 |
| 自动排布，可在部位内微调 | 默认自动放好；有需要时调位置和朝向 | 兼顾快速试装和造型表达 | 需要定义范围、遮挡、重排与保存语义；建议首轮不让微调影响战斗，但尚待用户确认 |
| 自由挂接，位置参与战斗 | 自选连接位置、方向，结构影响运动或命中 | 结构本身可以成为玩法 | 会引入连接、支撑、碰撞、瞄准等新规则，已超出当前按部位装配的模型 |

2026-11-25 用户已选第二种：默认自动排布，需要时在部位内调整位置和朝向；首轮微调只影响造型，不影响战斗。它兼顾已确认的外形创作与快速试组合。另两种作为被比较方案保留，不进入首轮。

“可微调”不等于任意跨部位安装；左右、前后、角度、缩放分别开放多少仍需细化。物理结构方案也不因讨论而加入首轮。

### 3.2 不论选哪档，都值得讨论的操作要求

以下均为提案：

- 快速安装不强迫精确拖拽；想造型时再进入细调，不给每次添加都增加确认步骤。
- 添加、减掉一个、同位置换件分别定义，不能把“加一件”暗中当作替换。
- 可以辨认刚装上的东西，知道刚改变了什么；零件多时仍能找到要改的对象。
- 试错可以撤销；清空后如何恢复也要交代。撤销与保存是不同需求。
- 支持保留一套装配再做局部比较，避免每次试验都先拆毁唯一方案。是否做多方案保存待定。
- 提供效果预览或可取消试装，但不强制所有操作都经过弹窗。
- 若提供对称或成对添加，必须说明“一次添加”究竟是一个实例还是一对，计数、属性和撤销要一致。
- 装配失败说明原因并保留原方案；满 64 件时不静默丢件、删旧件或只完成半次成对操作。

一条候选过程：选一件安装 → 看局部变化 → 再加、换或撤销 → 保留方案 → 试战 → 带着结果回到原装配继续改。

这只是流程草案，不等于方案保存、微调和对称添加已经获准。

## 4. 组合怎样配：建议先写部件作用，再写特殊组合

### 4.1 可选的组合来源

| 方式 | 玩家怎样获得新效果 | 适用性及风险 |
|---|---|---|
| 明确配方主导 | 指定 A 与 B 凑齐才给一个特色能力 | 好教、好列清单；可能变成照表装，未列入配方的搭配很空 |
| 通用作用为主，少量特殊组合 | 零件本身有作用，作用之间可以配合；少数组合追加特殊行为 | 当前建议。保留试验空间，也能控制首轮规模；仍须逐条定义自动触发、重复和冲突 |
| 物理涌现主导 | 支撑、重量、动力和几何关系自然产生表现 | 接近结构拼装；真实规律是否直观、成本是否值得承担都未验证 |

2026-11-25 用户已选第二种：零件单独有明确作用，不同作用可以配合，少数组合追加特殊行为。不采用明确配方主导，也不以物理结构自然涌现作为首轮基础。现有 24 件与五条协同不足以证明深度够或不够，不能先靠扩大零件量解决问题。

### 4.2 每个部件先有能说清的用途

可把已有部件整理为动作、攻击、承受伤害和辅助等设计职责；这些职责用于设计整理，不新增玩家的槽位或装备限制。

部件卡至少回答：单独装它有什么用；何时自动起效；玩家在哪里看出作用；重复装有什么变化；什么情况下无效；它给哪些其他作用提供条件。

纯数值件可以保留，但不能让所有零件只剩同一种数值相加。装饰性零件是否必须影响战斗，以及能否单独调整外观，也仍待讨论。

### 4.3 用现有零件做纸面例子

下表所有行为都是未批准、未实现、未验证的构想，不是现有能力说明，也不要求同时实现。

| 搭配例子 | 候选行为差异 | 必须补答的规则 |
|---|---|---|
| 弹簧腿 + 锤喙 | 起跳后尝试落地重击，强调攻击时机 | 谁触发、能否落空、落地后等待多久；重击是否需要两件同时在场 |
| 疾跑腿 + 独角 | 接近目标时冲刺攻击 | 只在首次接敌起效还是可重复；冲刺被阻止时怎样结束 |
| 精瘦鸡身 + 羽翼 | 产生滑翔或空中接近行为 | 是否真的引入高度；起降与对空规则如何闭合；不能只加滑翔标签 |
| 尖喙 + 爪腿 | 一次命中后发生可辨认的跟进攻击 | 哪个命中触发、爪能否命中、有没有触发间隔；不能让别处的 sharp 标签冒充尖喙 |

前两个也可以做成通用作用相互配合，而不是限定 ID 的隐藏配方。必须先确定组合来源，再决定例子采用哪种实现语义。

### 4.4 不靠大量隐藏配方制造深度

建议普通部件的用途和副作用可知，装上后能看到组合变化；发现新作用的乐趣可以来自试验。是否提前给搭配线索、是否保留隐藏组合，留作后续确认，不默认全公开或全隐藏。

每条组合需要回答：

1. 条件：是指定零件、某部位上的标签、数量，还是全身状态？标签来自哪里？
2. 效果：自动行为、命中关系、表现或数值到底改了什么？
3. 重复：相同组合装多份是增强、增加次数、共享触发间隔，还是仅造型变化？
4. 冲突：同时触发相反效果时，哪个最终生效，怎样解释？
5. 比较：什么情境它有用，什么情境换一种搭配更合适？
6. 反馈：装配时预测什么，战斗时发生什么，战后怎样指出原因？

暂不选定递减、能量、冷却或新容量等限制方案，也不宣称任一方案已能解决“越装越强”。重复挂载如何形成有效选择，必须专门验证。

## 5. 从讨论稿到可交给执行模型的文档

装配自由度与组合来源已确认，但部位与零件设定尚未闭合。按用户纠正，当前先梳理组装部位，不以单件作用为由提前展开战斗体系。部位与零件明确后，再把以下内容补成规则卡。具体行为仍须用户确认：

- 操作前状态、玩家动作、操作后状态，以及取消、撤销和失败恢复。
- 自动排布与人工调整冲突时怎么办；增删导致重排是否保留已调好的造型。
- 一个零件和一份组合的条件、来源、触发、叠加与最终效果。
- 典型过程、反例和验收情境，不把期待的表现写成已验证结论。
- 明确允许执行模型做什么、不能自行补什么；未决项遇到时反馈，不自行决定。

候选验收情境（尚未执行、没有接受阈值）：

- 连续装多件后删除目标实例，确认删的就是想删的对象。
- 替换与新增不会混淆；撤销后恢复原计数和属性。
- 多件、成对或批量操作撞上既有 64 件上限时，不造成半完成与丢件。
- 全身有 light 但身体并不轻、其他部件有 sharp 但喙不尖时，规则仍按已确认来源触发。
- 正向与冲突同时满足时，只把最终有效结果说成有效。
- 多份相同部件、多个自动行为同时满足时，有明确的叠加和调度结果。
- 回到装配后能对照上一次试战的方案与改动，而不是只记住输赢。

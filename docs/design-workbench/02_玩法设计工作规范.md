# 玩法设计工作规范

版本：V1.1

日期：2026-11-24

状态：文档与确认流程按用户本轮要求执行；具体玩法、指标和开发顺序均须另行确认。

## 1. 工作顺序

公开游戏的 GDD、设计师方法和产品说明有不同用途。不存在一份可以直接决定本项目玩法的通用强制 GDD。这里建立项目工作规范，之后随实际设计修订。

| 步骤 | 要回答的问题 | 产物 | 进入下一步的条件 |
|---|---|---|---|
| 研究 | 哪些做法已有公开依据？与我们哪里相似、哪里不同？ | 来源记录、案例对照 | 链接和正文已核验，事实与建议分开 |
| 定方向 | 玩家主要追求什么？先验证哪种游戏循环？ | 一页玩法概念、决策记录 | 用户确认首轮范围及暂不处理项 |
| 写循环 | 玩家得到什么信息、做什么选择、承担什么后果，如何继续？ | 状态/转移表与典型局过程 | 没有缺失的返回、失败或退出路径 |
| 写规则 | 零件和操作如何实际改变结果？ | 系统规则卡、交互矩阵 | 用户确认影响体验的规则取舍 |
| 验证 | 提议的体验是否发生？哪里卡住、哪里只有等待？ | 试验记录、测试结果 | 按事先确认的判据评价，不用事后改指标证明成功 |
| 查覆盖 | 在确定范围内，有哪些职责、状态与分支尚未回答？ | MECE 需求表、未决问题 | 每条有归属、状态、依赖与验证方法 |
| 实施与复验 | 改动是否实现已确认规则？是否引入副作用？ | 实现、测试和试玩记录 | 结果回填，偏差交用户决定 |

低成本研究和纸面推演可以先做。代码原型需要先确认试验范围；试验结果不自动成为正式玩法。

## 2. 每条结论的状态

- **已查证事实**：原文、代码或试验实际支持的内容；必须给出处或复现条件。
- **推论**：基于事实的解释；写清适用条件和可能反例。
- **提案**：可选的玩法或工作方案；列取舍和建议依据。
- **待用户确认**：仍需用户决定，或用户跳过未回答。
- **已确认**：记录确认日期、用户意思和范围；历史文档的旧确认注明来自旧文档。
- **已实施 / 已验证**：分开记录。实现完成不代表体验验证完成，单测通过不代表好玩。
- **延期 / 否决 / 被替代**：保留原因与替代项，避免再次误加入范围。

“推荐”“行业案例都这样”“用户没有反对”都不能代替明确确认。

## 3. 每个系统写到什么程度

使用 [系统规则卡模板](templates/系统规则卡.md)。至少包含：

1. 玩家为什么需要这个系统，解决哪个已确认体验目标。
2. 输入、前置条件、可做动作与不能做的动作。
3. 状态及转换条件；每次转换产生什么结果。
4. 数值、叠加顺序、优先级、上限、随机性和同 tick 冲突处理。
5. 对其他系统的影响，以及唯一的规则来源。
6. 正常例子、边界例子、失败例子、恢复路径。
7. 如何观察实际效果、如何验证、哪些答案还未确认。

例如“有翅膀可以飞”还缺命中关系、起降条件、重复装备与双方都无法攻击时的处理。先列问题，不直接替用户选择答案。可参考 [玩法细节拆解取证](research/玩法细节拆解_取证.md)。

## 4. 流畅性的检查口径

本轮不设计界面布局；仍需明确玩家能得到哪些玩法信息，否则无法验证选择是否成立。

先记录一条候选循环：

`了解挑战 → 组装/调整 → 确认出战 → 战斗 → 理解结果 → 决定重试、继续或退出`

这条路径用于检查现有设计，不是对关卡制、商店制或探索制的定案。不同方向的循环由用户确认后分别展开。

每个环节检查：

| 维度 | 问题 | 可记录的观察 |
|---|---|---|
| 决策 | 玩家此时知道什么，至少有什么可比较的方案？ | 实际改装理由、使用/放弃的方案 |
| 因果 | 装配差异是否在后续战斗中产生可解释的差异？ | 行为变化、事件差异、胜负或资源消耗 |
| 等待 | 玩家在等加载、动画、自动结果，还是在思考？ | 真实模拟时长、播放时长、主动操作时间分开记 |
| 失败恢复 | 输后保留什么、失去什么，多久能验证新想法？ | 失败到下一次有效尝试的时间和步骤 |
| 继续动机 | 赢后出现新挑战、新组合还是单纯数值增加？ | 玩家是否能说出下一次想试什么 |
| 中断 | 离开、重进、重播、版本变化如何影响当前局？ | 丢失的进度、重复结算、不可恢复状态 |

时长、成功率、组合数量等指标先列为待确认；不能自行认定某个秒数或比例就是合格线。主观“顺畅”需结合玩家描述和可观测行为，不能仅用完成时长替代。

## 5. 组装对战专项检查

- 零件是否改变行为、攻击关系、时机或资源使用？纯数值件也可以存在，但要有明确用途。
- 是否存在一直加装而没有代价的支配策略？先固定敌人、规则和随机条件验证，再讨论限制方式。
- 重复部件、跨槽协同、冲突、互斥、叠加上限如何结算？
- 一个组合的收益与代价能否被玩家理解？是否有其他可行解？
- 敌人的威胁是否明确，失败是否能产生下一次调整的线索？
- 战前信息是否足够？隐藏信息与随机性是否允许玩家形成有效预期？
- 如果引入主动操作，胜负中组装与操作各承担什么作用？
- 若加入探索，损坏、维修、掉落、携带、返程是否给组装增加新的选择？

这里的检查问题不等于已决定加入预算、硬容量、飞行、合成或探索。

## 6. MECE 在本项目怎么用

MECE 用于检查明确边界内的需求归属与遗漏，不能证明游戏所有可能性已穷尽，更不能代替试玩判断。

首轮分解建议按“系统主要责任”划分，待用户确认范围后使用：

- 对局流程：开始、阶段转换、结束、重试、暂停/中断。
- 组装：可用部件、装卸、合法性、组合派生。
- 战斗：行为、命中、伤害/效果、胜负。
- 挑战内容：敌人、关卡/遭遇、难度与变化。
- 成长与资源：取得、消耗、保留、重置；是否启用待定。
- 持久化与规则版本：存取、恢复、兼容、回放规则基线。

每条需求只给一个主要归属；其他系统通过依赖关系引用，避免重复定义。同一层不要把“功能系统”“开发阶段”“玩家类型”混在一起。

然后另用覆盖矩阵检查“系统 × 正常/失败/边界/中断/恢复”，再用交互矩阵检查系统间组合。未选定的大世界、多人或商业化记为范围外候选，不能为了凑全目录提前设计。

需求最小字段：`ID、主要归属、玩家目的、规则、状态、依赖、依据、确认记录、验证方法、验证结果`。

## 7. 文档和实现同步

- `docs/DESIGN.md` 保留既有设计；本轮研究集中在 `docs/design-workbench/`。用户确认改动后再更新正式设计，防止两份有效规则并存。
- `docs/INTERFACES.md` 负责数据与协议，不替代玩法说明；若变更玩法语义，先记录决定，再同步接口与代码。
- 规则用稳定 ID 互相引用，例如 `ASM-*`、`CBT-*`；具体 ID 在范围确认后分配，不先生成空需求。
- 更新内容后同步根目录 `Agent.md`、文档导航、决策记录和验证记录。
- 文档工作版本与游戏业务版本、JSON/协议版本分别管理。
- Git 提交前检查范围、链接、文档版本、未确认措辞与敏感信息；推送前拉取远端状态，出现冲突保留双方内容并处理，不强推。

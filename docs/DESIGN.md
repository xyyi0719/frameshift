# 拼装小鸡 · Build-a-Chick

> 设计文档 v0.1 · 2026-11-23
> 一句话：**一只什么都没有的小鸡，靠你给它装上的零件去打架。**
> 目标形态：先网页可玩（实时预览），再上微信小游戏 / 抖音小游戏；单机 PvE 先行，双人对线随后。

---

## 0. 现状与目标

| 阶段 | 内容 | 判据 |
|---|---|---|
| M0（本周） | 网页预览版：装配 + 一场 PvE | 打开链接就能把零件拖到鸡身上并打完一关 |
| M1 | 8 关 PvE、结算成长 | 完整单机循环，可留存 |
| M2 | 异步 PvP（打对手快照） | 无需服务器实时，先把"对线"跑通 |
| M3 | 实时 PvP + 微信/抖音上架 | 帧同步/状态同步 + 平台适配 |

旧的《Frameshift》已从仓库移除，留在 tag `frameshift-v1`（线上旧版本仍可访问，直到新版本部署覆盖）。

## 1. 核心循环

```
选关 → 装配（拖零件到鸡身上，**M0 不设解锁限制，零件全开**）→ 自动战斗 → 结算 → 回装配
```

> M0/M1 采用**自由装配**：所有零件一开始就可用，先验证"组合好不好玩"，
> 解锁与货币放到 M2 之后再谈（配置表保留 `unlock` 字段但运行期不校验）。

三个必须成立的手感：

1. **装上去立刻不一样**：属性条、外形、战斗表现都要在 1 秒内可见地变化。
2. **组合有惊喜**：两个零件放一起会产生协同或冲突（翼 + 重甲 = 飞不起来）。
3. **一眼看懂为什么输**：结算要指出"被谁的什么属性压制"。

## 2. 生物组装系统

### 2.1 骨架与槽位

小鸡有一副固定骨架，**6 个槽位**，随阶段解锁：

| 槽位 | 说明 | 解锁阶段 |
|---|---|---|
| `body` 躯干 | 决定基础 HP 与负重上限 | 幼体（起手即有） |
| `beak` 喙 | 主要输出手段 | 幼体 |
| `legs` 腿 | 移速、冲撞、跳劈 | 亚成体 |
| `wings` 翼 | 飞行、滑翔、俯冲 | 亚成体 |
| `tail` 尾 | 平衡、扫击、稳定 | 完全体 |
| `crest` 头冠/附加 | 特殊能力（毒、吼、护盾） | 完全体 |

> **M0 例外**：6 个槽位全部解锁，不按阶段限制，方便直接试各种组合；
> 阶段系统保留在数据里（`stage` 字段），等验证完玩法再决定是否启用。

- 每个槽位有 **尺寸容量**（`size` 1–3），部件也有尺寸；**放不下就是放不下**（躯干越大容量越大）。
- 部件有 **重量**，总重量影响移速与"能否起飞"。

### 2.2 部件（Part）

```ts
PartDef = {
  id: 'leg.spring',        // 命名空间化，便于扩展
  slot: 'legs',
  tier: 1,                 // 1 基础 / 2 进阶 / 3 稀有
  size: 2,                 // 占槽容量
  mass: 3,                 // 重量
  stats: { hp: 0, atk: 2, def: 0, spd: 4 },
  tags: ['jump', 'light'], // 供组合规则匹配
  ability: 'leap_slam',    // 战斗中的主动技（可选）
  art: 'leg_spring',       // 渲染 key，不含资源路径
}
```

**数量规划**：首发 24 个部件（每槽 4 个），M1 扩到 40。所有部件走 `parts.json` 配置表，代码里不写死。

### 2.3 组合规则（这是游戏的灵魂）

用**标签匹配 + 数值修正**表达，不写 if-else 特例：

| 类型 | 例子 | 表现 |
|---|---|---|
| 协同 | `wing` + `light` → 获得 `glide` | 空中停留，躲避地面攻击 |
| 冲突 | `wing` + 总重 > 阈值 → `grounded` | 翼收起，属性减半，UI 明确提示 |
| 转化 | `beak.sharp` + `legs.claw` → 连击 | 攻击附带一次追击 |
| 进化 | 同槽同 tier 两个部件 → 合成高一级 | 装配界面直接拖到一起 |

规则表同样数据化（`synergies.json`），M0 先内置 5 条，M1 扩到 20 条。

### 2.4 阶段成长

```
幼体(2槽) --通关1-3--> 亚成体(4槽) --通关4-6--> 完全体(6槽)
```

阶段只解锁槽位和少量基础属性，**不搞无限数值养成**（避免滚服感）。长期成长靠"解锁更多部件 + 更多组合"。

## 3. 战斗系统

### 3.1 形式

- **自动战斗 + 一次主动技**：小鸡自动前进、自动攻击；玩家在关键时刻点一次部件技能（每局 1 次）。
- 场地是**一维对线**：我方在左、敌方在右，相向推进，接触后进入交战。
- 单局 **30–60 秒**，30 tick/s 固定步长。

选自动战斗而不是全手动，原因：微信/抖音小游戏的目标用户是碎片时间，且**确定性模拟**能让 PvP 与防作弊简单一个量级（见 `INTERFACES.md`）。

### 3.2 数值模型（v0）

```
HP    = 20 + body.hp*2 + Σ parts.hp
ATK   = beak.atk * 2 + Σ parts.atk
DEF   = Σ parts.def
SPD   = 100 * (1 - clamp(totalMass / capacity, 0, 0.6))
DPS   = ATK * 1.2 / (1 + DEF*0.05)
TTK   ≈ HP / DPS   → 目标落在 8–20 秒
```

判定：一方 HP ≤ 0；或到时（60s）比剩余 HP 百分比。

### 3.3 战斗事件

战斗不直接改渲染状态，而是产出**事件流**（`hit`, `crit`, `block`, `heal`, `die`, `ability`），渲染层消费事件做表现。这样：回放、观战、服务端校验、异步 PvP 全部复用同一套。

| 关 | 敌人 | 教学点 |

## 5. PvP 对线

### 5.1 M2 异步（先做）

上传 `CreatureSnapshot` 作为"影子"，对手打你的影子，双方各自结算。优点：零服务器压力、可离线、适合小游戏冷启动。

### 5.2 M3 实时

- 30Hz 状态同步，客户端只发**指令**（移动/技能），服务端（或房主）跑模拟。
- 每 30 tick 校验一次状态哈希，不一致即回滚重放。
- 断线 10 秒内可重连（保留 tick 缓冲）。

### 5.3 平衡原则

PvP 只用"完全体"，且部件全部解锁（PvP 不卖数值）；PvE 的成长只影响 PvE。

## 6. 平台与合规

| 平台 | 主包 | 总包 | 备注 |
|---|---|---|---|
| 微信小游戏 | ≤ 4 MB | ≤ 30 MB | 单个普通分包不限，独立分包 ≤ 4 MB；有官方帧同步服务 |
| 抖音小游戏 | ≤ 4 MB | ≤ 20 MB | 超出部分走 CDN 资源服务器 |

- 这是硬约束，直接决定**引擎选型**与**美术规格**（见 §7）。
- 合规：需**软件著作权**；纯广告变现通常还要备案/资质，**一旦有内购就必须有版号**。M0–M2 期间不接支付，先把产品做出来。

## 7. 技术架构

### 7.1 分层

```
┌──────────────── 表现层（伪 3D，可替换）────────────────┐
│ Three.js / WebGL：低多边形鸡 + 零件 + 场景                 │
│ 固定斜 45° 相机 · 卡通着色 · 程序化动画（无骨骼也可）        │
└────────────────────────▲────────────────────────────────┘
                         │ 只读状态 + 事件流（不反向写）
┌────────────────────────┴────────────────────────────────┐
│ 逻辑内核（纯 TS，无 WebGL/DOM，可单测、可跑在 Node）        │
│ 组装校验 · 属性推导 · 战斗模拟（2D 一维对线）· 结算          │
└────────────────────────▲────────────────────────────────┘
                         │ JSON 配置
┌────────────────────────┴────────────────────────────────┐
│ 数据层：parts / synergies / levels / enemies / rigs        │
└─────────────────────────────────────────────────────────┘
```

**两条关键决策：**

1. **逻辑内核不依赖任何渲染/平台 API**，同一份战斗代码可跑在网页、微信、抖音、Node（服务端校验、批量平衡测试）。
2. **伪 3D 只发生在表现层**：战斗判定仍然是"一维对线 + 30Hz 确定性模拟"，3D 只是把双方摆在一个有纵深的场地上。这样 PvP 的同步量不会因为画面升级而爆炸，回放与校验也不受影响。

**关键决策：逻辑内核不依赖任何渲染/平台 API。** 这样同一份战斗代码可以跑在：网页、微信、抖音、Node（服务端校验、跑批平衡测试）。也是"网页先预览、之后上小游戏"最省事的路径。

### 7.2 为什么用 Three.js 而不是 Cocos

- 伪 3D 需要真正的 3D 管线（深度、光照、相机），Canvas 2D 做不出可信的低多边形质感。
- Cocos/Laya 的编辑器资产（场景、预制体）不适合用代码/AI 代理维护，迭代慢；几何与材质全部**代码生成**（`BufferGeometry` + 程序化材质）才能快速试错。
- Three.js 压缩后约 600 KB，加上游戏逻辑与数据，主包可控制在 **2 MB 以内**，满足微信/抖音 4 MB 主包限制；其余贴图/音效走分包或 CDN。
- 迁移成本可控：Three.js 在微信小游戏有成熟适配（`weapp-adapter` + 官方 WebGL 支持），抖音同理。

### 7.2.1 伪 3D 的视觉规格（M0）

| 项 | 设定 |
|---|---|
| 相机 | 固定斜 45° 透视（fov 35），不做自由旋转，避免玩家迷失 |
| 模型 | 低多边形，单个零件 ≤ 300 三角面，鸡身 ≤ 1200 面 |
| 材质 | 卡通着色（三段色阶）+ 深色描边（`EdgesGeometry` 或反向法线壳） |
| 光照 | 一盏主平行光 + 一盏补光 + 环境光，阴影用贴地 blob（省性能） |
| 动画 | 程序化变换：零件按槽位锚点挂载，用 sin/缓动驱动呼吸、扇翼、迈步，先不做骨骼蒙皮 |
| 场地 | 一条有纵深的跑道（2.5D），双方沿 x 轴相向，z 轴用于景深与错位 |
| 分辨率 | 逻辑分辨率 1280×720 自适应；移动端限制 DPR ≤ 2 |
- 若后期需要更复杂特效，再迁 Cocos，逻辑内核可原样搬走。

### 7.3 确定性

- 固定步长 30Hz，全部用整数/定点数运算。
- 随机数用**种子 RNG**（xorshift128），回放只需 `seed + 指令序列`。
- 同样的输入必须产生同样的输出（有单测守护）。

## 9. 已确认的决策

| 问题 | 结论 |
|---|---|
| 装配时机 | **战前装配**，战斗中不改装备 |
| 战斗操作 | **自动战斗 + 每局 1 次主动技** |
| 部件获取 | **M0/M1 自由装配**：不做解锁、不做货币，先验证组合玩法 |
| 美术 | **伪 3D 低多边形**（Three.js，固定斜 45°，卡通着色 + 描边） |
| 首发平台 | 微信先，抖音随后 |
| PvP | 先单机打磨，M2 上异步 PvP，M3 再实时 |
| 变现 | 先纯广告（M0–M2 不接支付，不申请版号） |

## 10. 仍待定

- 视角与镜头运动：固定 45° 是否会挡住"翅膀/腿"的辨识？M0 先做一版再评估。
- 组装是否需要"重量上限"约束（现在完全自由，可能出现"全装最强"的单一解）。
- 战斗是否需要第二只生物（多单位）——当前按单只设计。
- 学步期几乎必踩的坑：伪 3D 下零件遮挡与拾取判定（点选槽位还是点选零件？M0 先做侧栏列表点选）。
